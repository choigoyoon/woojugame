# 안드로이드 공통 프레임 최적화 검증

검증일: 2026년 11월 21일(KST). 비교 기준 커밋: `40007f3`.

이 문서는 `3232693`의 최적화 측정 이력이다. 이후 사용자 요청으로 현재 렌더링 목표/상한을 60fps로 변경했다. 아래의 무제한 RAF 설명은 이전 구현을 가리키며, 현재 정책은 README와 PLAN의 H를 따른다.

## 적용 내용

브라우저의 RAF마다 렌더링하며 별도의 60fps 제한이나 프레임 생성 타이머를 두지 않는다. 50ms 클램프·5ms 물리 틱·100ms 입력 버퍼를 유지한다. 모델명을 검사하지 않아 안드로이드 폰·폴드·태블릿에 같은 정책을 적용한다.

- 광장 64칸 바닥과 배경, 러너의 상태별 문장 슬롯/점프 버튼/헤더, 공통 코인/홈 아이콘을 Canvas 레이어로 재사용한다. 캐시는 실제 내부 픽셀 밀도에 맞춰 재생성하고, 중첩된 작은 레이어에서도 원래 밀도를 유지한다. OffscreenCanvas가 없으면 일반 Canvas로 공통 캐시를 만든다.
- 별의 단위 좌표를 재사용하고 다각형 경계·그라데이션 계산의 임시 배열을 줄인다.
- 투시 보스의 팔/주먹/모자를 고정 크기 모델로 저장한 뒤 확대한다. 매 프레임 달라지는 소수점 크기로 캐시를 생성하지 않는다. 부대 파츠 변경 감지도 매 프레임 JSON 직렬화 대신 팔레트 참조를 비교한다. 장착 변경 시 부대와 HUD를 함께 갱신한다.
- 프레임 주기와 JS 작업 비용을 1초 창으로 관찰한다. 시작/모드 변경/복귀 뒤 1.2초 대기하고 과부하가 두 창 이어질 때 내부 밀도를 12.5%씩, 최소 75%까지 낮춘다. 변경 간격은 최소 4초, 회복은 15초 이상의 여유 후 한 단계씩이다. DPR은 최대 2, 최소 1이다. 최대 픽셀 수 절감은 약 44%다.
- 품질 조정은 다음 RAF의 그리기 전에 처리한다. CSS 배치·조작 좌표·진행 상태와 누른 터치를 유지한다. 동일한 크기의 중복 resize 통지는 무시하고, 실제 회전/폴드 크기 변경은 기존대로 입력을 해제한다.
- 절전으로 일정하게 낮아진 RAF와 저비용 그리기만 관측되면 무작정 화질을 낮추지 않는다. Canvas 2D 관측만으로 안정적인 GPU 병목과 OS 제한을 완전히 구별할 수는 없다.

## 렌더링 비용 비교

Linux Chromium 156, 412×915 CSS, DPR 2. 실제 프로덕션 렌더러에 동일한 시드의 장면을 주고 120Hz 간격의 애니메이션 상태를 샘플링한다. 장면마다 180회 그린 뒤 앞 30회를 제외한다. 매회 `getImageData(1,1,1,1)`로 래스터 작업을 완료시켜 그리기+읽기 시간을 잰다. **디스플레이의 120fps 측정이 아니며 읽기 비용도 포함한다.** 다른 무거운 테스트와 동시에 실행하지 않았다.

초기 단일 측정에서 배틀의 실행 간 편차가 있어 이전 커밋과 현재 코드를 3회씩 번갈아 실행했다. 다음은 각 실행 평균의 중앙값(ms)이다.

| 계단 | 8.45 | 8.14 | -3.6% |
| 배틀 일반 | 11.43 | 10.50 | -8.1% |
| 배틀 보스 | 13.93 | 11.71 | -15.9% |
| 러너 | 11.13 | 8.49 | -23.7% |

원시 결과: `test-results/arcade/render-paired-{before,after}-{1,2,3}.json`, 집계 `render-comparison.json`. 측정 시점의 같은 호스트 비교이며 안드로이드 전체 모델의 속도 향상률로 일반화하지 않는다.

## 실제 시간 RAF 측정

각 모드에서 25초 동안 실제 터치 입력을 주입했다. 브라우저 RAF는 이 환경에서 약 60Hz다. 네 모드 모두 정상 밀도(scale 1)를 유지했다.

| 모드 | 평균 FPS | p95 프레임 ms | p99 프레임 ms | 50ms 초과 long task |
| --- | ---: | ---: | ---: | ---: |
| 계단 | 59.72 | 16.8 | 16.8 | 0 |
| 배틀 일반 | 59.60 | 16.8 | 16.8 | 0 |
| 러너 | 59.80 | 16.7 | 16.8 | 1 |
| 광장 | 60.00 | 16.8 | 16.8 | 0 |

변경 전 평균은 계단 59.72, 배틀 59.68, 러너/광장 59.80fps였다. 이 60Hz 환경의 평균 FPS는 이미 상한에 가깝다. 이번 변화는 고주사율과 더 느린 기기를 위한 렌더링 여유를 확보한 것이며, 화면 주사율을 초과하는 FPS 상승을 주장하지 않는다. 러너에서 57ms long task 1회가 관측되었으므로 끊김 0건으로 보고하지 않는다. 결과: `fps-before.json`, `fps-after.json`.

## 아직 실측하지 않은 항목

실제 Android 기기의 90/120Hz 지속 성능, 장시간 발열·배터리·제조사 절전 정책은 미측정이다. 60Hz 패널에서 120개의 서로 다른 프레임을 표시할 수 없으며, 120Hz 패널도 브라우저가 60Hz만 제공하면 앱이 강제로 해제할 수 없다. 모든 안드로이드 모델의 특정 FPS나 완전한 무결점 동작을 보증하는 결과가 아니다.

## 후속 변경: 60fps 목표

사용자 지시에 따라 `CONFIG.performance.targetFps=60`을 적용했다. 90/120Hz RAF에서 기한의 나머지를 보존해 평균 60회 렌더링하고, 지연된 프레임을 몰아서 재생하지 않는다. 기본 60Hz에서는 디스플레이 시계의 미세한 드리프트에 맞춰 기준을 재설정한다. 첫 구현에서 확인된 불필요한 프레임 건너뜀을 이 방식으로 수정했다. 90Hz에서는 화면 주기의 정수 배수로만 표시할 수 있으므로 1회/2회 주기 간격이 번갈아 나타날 수 있다.

자동 해상도는 표시한 프레임과 60fps의 작업 예산을 사용한다. 90Hz 화면에서 정상적인 11/22ms 교대 간격을 과부하로 오인하지 않는다. `performance.cadenceHz`는 렌더링 간격 관측값, `targetFps`는 설정한 목표다. 기존 진단의 `rafHz` 이름을 변경했다.

- 전체 Node 테스트 93개 통과. 그중 프레임 정책/배치 23개에 30/59.94/60/61/90/120/144/240Hz 입력, 시계 드리프트, 중단/복귀와 몰아서 그리기 방지를 포함한다.
- 프레임 배치를 거친 실제 전투 시뮬레이션에서도 60/90/120Hz의 10초 경과 시간·이동 거리·연사 수·보상이 동일함을 확인했다.
- 실제 터치의 장착/PIN·문장·배달/36개 화면 조합, 자동 해상도 전환 중 터치 유지, 오프라인 재시작/실패 업데이트 검사를 통과했다.
- 성능 검사는 브라우저 RAF 빈도와 실제 게임 렌더링 횟수를 따로 기록한다. 60fps 상한이 걸린 앱에서 RAF 빈도만으로 게임 FPS를 보고하지 않는다.

게임 우선 재설계는 README와 PLAN H에 반영한 후속 방향이다. 이번 변경에서 미니게임 콘텐츠를 다시 구현한 것은 아니다.
